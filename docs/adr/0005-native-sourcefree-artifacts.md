# ADR 0005：客户原生管理安装包不分发应用源码

- 状态：用户批准，实施中；不代表已发布或已通过空白机器验收。
- 日期：2026-10-09

## 决策

客户安装包交付已签名的 Linux 程序、Web 产物、迁移和运行依赖及必需的安装脚本，不交付应用源码仓库、`source.bundle` 或 Git 历史。发布端仍保留私有 Git，验证精确已推送提交、完整对象、tree、祖先关系、迁移完整集合及源码内容，不能用签名替代这些发布检查。

原生 release v2 增加 `key_id`，用独立 Ed25519 制品密钥签署 `cdnca.native-management.release/v2\n` 加未经重编码的 `release.manifest.json` 字节。`release.manifest.sig` 是标准 Base64 的 64 字节签名，可带一个末尾换行，最大 128 字节，是 tar 中独立的普通 0644 文件，不进入 manifest 的 `files`，避免自引用。先完成内层签名和 tar，再计算制品摘要并签署执行计划、外层安装包。

制品信任文件由包外独立配置；格式为 `{"version":1,"keys":[{"key_id":"...","public_key_pem":"..."}]}`，只接受 Ed25519，拒绝未知字段、重复 key ID 和空集合。客户不得接受包自带的信任根。轮换时保留 current/previous 所需的旧公钥，直到回滚窗口结束。

外层安装包 v2 使用自己的签名域 `cdnca.native-management.install/v2\n`，固定白名单用 `release.manifest.sig` 替换 `source.bundle`。在激活、执行程序或安装写入前，验证外层签名、全部文件摘要和内层签名。运行期间每次 archive、directory、Probe、health、rollback/restart 验证均使用内层签名，不依赖已经过期的执行计划来证明当前版本身份。

短时签名计划继续约束谁可在何时升级到哪个精确 tar 摘要；长期制品签名只证明版本与文件来源，不授予执行权限。客户 v2 保留版本单调增长、精确 previous commit、平台、文件兼容、迁移不变、双锁、维护状态、原子切换和整包回滚检查。

## 兼容与边界

- v1 私有包和已有 v1 主控继续要求原来的受保护 Git 来源验证；不得因为配置了公钥而跳过 v1 的 Git 检查。
- v1 转 v2 必须先受控更新独立 runner 和信任配置，并保留 v1 回滚所需的 Git。v2 升级到 v1 被拒绝；显式故障回滚仍需验证实际 previous 的格式和完整证据。
- 首装签名证明真实性，不单独证明它是全局“最新”。公开入口版本、制品摘要、已推送提交和实际运行版本必须另行核对；没有防冻结协议时不声称抵抗可信旧包重放。
- 不删除 current/previous、身份、数据库、证书、配置或私有发布端源码；客户不带源码不等于清理已有回滚证据。
- 真实空白主机安装、自动启动、管理与节点绑定及浏览器验收是独立发布门禁，单元测试不能代替。
